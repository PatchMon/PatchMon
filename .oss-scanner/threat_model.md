# Threat model

PatchMon monitors and patches other people's machines. The server is a single Go binary with an embedded web UI. An agent on each host dials out to that server, reports installed packages, and can be told to apply updates or open a remote session. A vulnerability here can reach every host an operator monitors.

This file is the scope and severity guide for an automated scan. It follows `SECURITY.md`, with one refinement: a finding that crosses from one user, host, or installation into another stays in scope even when the caller is an administrator of one installation or a compromised enrolled host.

## What to treat as untrusted

- Any HTTP request to the server. That includes login, session refresh, password reset, auto-enrolment, health, and the public OpenAPI document.
- Traffic from an enrolled agent: package reports, compliance results, and WebSocket messages. A monitored host can be compromised, so a valid host API key does not make its body trustworthy.
- Text that is stored and later shown to a person: host names, package names, notes, command output, compliance results.
- OIDC and Discord assertions, when those login methods are enabled.
- An auto-enrolment token, and an integration API token. Each has a limited job. A finding that lets one of them do more than that job is in scope.
- Paths, package names, and commands the server sends to an agent, once some caller who should not control that host can influence them.

The agent trusts the server it enrolled with. "The server told its own agent to run a command" is the product. Report that only when an unauthenticated caller, a low-privilege user, a different host's credential, or an enrolment token can cause the command.

## Components that matter most

In order:

1. Sign-in and sessions (`server-source-code/internal/handler` auth code, `internal/middleware`). Authentication bypass, session theft, and account enumeration are in scope. The dummy bcrypt comparison and the lockout are deliberate. Until the password has been proved, a real account, an unknown name, a disabled account, and an account with no password must answer the same way, in body and in timing. A difference on those paths is a bug. A suggestion to remove the dummy hash is not. After bcrypt succeeds, a disabled account answers `Account is disabled`. That split is deliberate, so a guesser cannot confirm the account. Do not report it, and do not patch it out.
2. Authorisation (`RequirePermission`, `internal/handler/role_guard.go`). A user gaining a permission their role does not have is in scope, including by editing a role, another user, or an OIDC default role.
3. Host API keys (`X-API-ID` and `X-API-KEY`, checked with `util.VerifyAPIKey` in the agent handlers) and auto-enrolment (`internal/handler/auto_enrollment.go`). One host's credential must not act on another host. An enrolment token may re-issue a key only for a host that token created and that has never reported. `host_id` is not a secret.
4. Code execution on a monitored host: patch jobs, the agent command path, the SSH terminal, and the RDP tunnel (`internal/sshproxy`, the guacd client, and the agent). The per-session RDP listener is unauthenticated on purpose and must stay on `127.0.0.1`. A report that only restates that, with no way to reach it off loopback, is not a vulnerability. `proxy_host` is bound to the enrolled host. A way to point it somewhere else is in scope.
5. SQL built from request or agent input. Queries are generated by sqlc from `server-source-code/internal/sqlc/queries`. Do not file a patch against `internal/db/`. That tree is generated.
6. The agent, `agent-source-code/`. It runs as a privileged service. Command injection and path traversal while applying updates are in scope.
7. The web UI, `frontend/src`, where agent-supplied or user-supplied text is rendered as HTML.

Also in scope: the install scripts embedded from `server-source-code/internal/agents/`, and the official Docker files under `docker/`.

The same server binary can select a database and a Redis per request when it is run for more than one installation. That selection lives in `server-source-code/internal/context`. A bug that lets one of those installations read or write another's data is in scope, including when the caller is an administrator of one installation or a compromised enrolled host. Services that are not in this repository (the hosted control plane, billing, the database proxy) are out of scope. Do not file findings about code you cannot see.

## How to exercise it

Binaries, with symbols, are at:

- `/src/build/patchmon-server`
- `/src/build/migrate`
- `/src/build/patchmon-agent`

Tests:

- `cd /src/server-source-code && go test ./... -count=1`
- `cd /src/agent-source-code && go test ./... -count=1`
- `cd /src && npm run test:run --workspace=frontend`

`go test` skips a test that needs `PATCHMON_TEST_DATABASE_URL`. This image does not run Postgres or Redis. A unit test, or a request against a server started in this container, is enough for an authentication, authorisation, injection, or path bug. The repository `.dockerignore` leaves `.git` out of the image build. If `/src` has history, use it to bisect. If it does not, bisect from the clone.

## How to rate severity

- Critical: unauthenticated remote code execution on the server or on a monitored host; authentication bypass; a host API key, enrolment token, or low-privilege session that can run commands or open SSH or RDP on a host it should not reach; one installation reading or writing another's data; theft of session cookies, API keys, enrolment secrets, or the JWT signing secret.
- High: SQL injection, command injection, or path traversal reachable by an enrolled agent or by a signed-in user who should not have that reach; cross-site scripting where agent or user input runs in another person's session; privilege escalation between roles; an enrolment token re-keying a host that has already reported.
- Medium: denial of service that an unauthenticated client can trigger cheaply; cross-site request forgery that changes a security setting; a signed-in user seeing another host's inventory or credentials inside the same installation when their role should not. Denial of service that needs a large volume of authenticated requests is low.
- Low: missing headers, verbose errors, version disclosure, and issues that need an existing administrator and stay inside that administrator's own installation.

Do not raise the rating because the project is security software. Rate the bug by who can reach it and what they receive.

We asked for email at high and above. Spend the report on critical and high. A medium that you believe is really a high should be argued as a high, not filed as a medium.

## What to leave alone

- A report that needs an existing administrator of one installation, or an already compromised host, and stays inside that installation and that host. A cross into another user, another host, or another installation is still in scope, including when the caller is that administrator or that compromised host.
- A dependency issue that is already public and is waiting on an upstream fix. Mention it if you like. It is not a new finding in this code.
- The marketing site at `patchmon.net`, social engineering, and anything outside this repository.
- Style, speculative hardening, and denial of service by filling a disk with an administrator's own logs.
- Generated code under `server-source-code/internal/db/`.

## How to write the report

One finding per root cause. Deduplicate on the vulnerable function, not on each caller.

Prefer a reproducer that runs offline in this image. A Go test or a small HTTP request is more useful than a description.

The candidate patch should be the smallest change that fixes the bug and keeps the existing tests passing. Do not refactor around it.

If we ship a fix, the commit credit is: `Discovered by Anthropic's OSS Scanner, as vulnerability ANT-...`
